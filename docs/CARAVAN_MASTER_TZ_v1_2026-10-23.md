**Версія:** 1.0 — консолідована робоча специфікація

**Репозиторій:** https://github.com/mavkaoblik-hub/fantastic-lamp

**Статус документа:** цільове ТЗ + матриця фактичної готовності; не свідчить про готовність усієї гри.

## 1. Підстава та ключові рішення

Документ узагальнює два надані матеріали — `вимоги до інтерфейсу.docx` (принципи HUD, камери, сенсорного керування) та `ТЗ.docx` (адаптація цих принципів до управління потягом) — і звірений із кодом та ресурсами `fantastic-lamp`. Оригінальні документи описують **UI/UX**, а не повну економіку, сюжет, бойову систему чи баланс. Такі доповнення нижче є проєктними рішеннями або планом, а не цитатами з джерел.

1. **Не копіювати сховище.** Центральний об'єкт — потяг з горизонтально з'єднаними вагонами, персоналом і внутрішніми приміщеннями. Ідеї з Fallout Shelter — лише ергономічні аналогії.
2. **Не змінювати затверджений художній стиль.** Дозволений стандарт — деталізований кінематографічний постапокаліптичний painterly-dieselpunk: іржава сталь, заклепки, латунь, лампи бурштинового кольору, синьо-чорні тіні. Геометричні SVG — технічні прототипи, не фінальна графіка.
3. **Одна функція — один канонічний арт-ресурс.** Для кнопки «Завдання», кожної валюти, ресурсу чи стану використовуємо єдиний ID з каталогу. Не створювати паралельний значок для іншого екрана.
4. **Єдина основна збірка Android.** До доведення vertical slice використовувати існуючу Android WebView-оболонку та один узгоджений набір HTML/JS/assets. Godot зберігати як експериментальний напрям, а не другу конкуруючу «готову» версію.
5. **Офлайн за замовчуванням.** Основні дії, сцена та збереження мають працювати без Інтернету; платні платежі та онлайн-мультиплеєр не входять до цієї версії ТЗ.
6. **Критерій «готово» — не просто коміт.** Потрібні: наявність усіх файлів, автоматична перевірка, успішна APK, ручний Android-тест, відсутність регресій і записаний результат.

## 2. Результат, який потрібно отримати

Гравець запускає гру, бачить постапокаліптичний потяг, керує оглядом, вибирає вагони, призначає людей, підтримує ресурси, розвиває склад, обирає наступну станцію, здійснює рейс, розв'язує події, отримує винагороду та зберігає прогрес. Кожна дія має видимий наслідок на HUD і, де застосовно, у світі гри.

### 2.1. Межі першої справді ігрової версії (MVP)

**Входить:** цілісний Android APK; старт/продовження; горизонтальна 2D-сцена; камера у трьох режимах; HUD; меню завдань; каталог вагонів; інвентар; персонажі й доручення; ресурси/баланс; зупинки й поїздки; основні випадкові події; локальне збереження; придатні для сцени PNG; стабільна робота без мережі.

**Після MVP:** складний бойовий тактичний режим, великі сюжетні гілки, фракційна економіка з п'ятьма активними валютами, онлайн-функції, платіжна система. Наявність графіки таких систем не означає, що їхні правила вже визначено.

## 6. Геймплей, ресурси та прогрес

### 6.1. Обов'язковий ігровий цикл

1. **Зупинка:** перегляд стану потяга, потреб, подій і доступних станцій.
2. **Планування:** вибір маршруту, завдань екіпажу, вагонів і модернізацій.
3. **Дія:** виробництво/збір ресурсів, ремонт, розвідка та взаємодія з подіями.
4. **Рейс:** перевірка запасів, запуск, анімація переміщення, витрати ресурсу та випадкова подія.
5. **Прибуття:** підсумок рейсу, нагорода/штраф, нові можливості та автоматичне збереження.

### 6.3. Валюти: облікова модель, а не припущення про монетизацію

Затверджений графічний атлас уже містить **п'ять позначок**: талони каравану, металеві жетони, торгові чеки, репутація, боргові знаки. Для ТЗ фіксуємо ці **унікальні назви та значки**. Використання в економіці вводимо поетапно: талони — запропонована базова валюта; жетони — можливий рідкісний ресурс; торгові чеки — торгівля; репутація — показник відносин; боргові знаки — спеціальні події. Ці функції є **дизайн-пропозицією**, адже надані DOCX не встановлюють їхніх правил. Жодних реальних платежів чи premium-shop без окремого рішення.

## 8. Технічна архітектура та реліз

- **Основне джерело версії:** одна web-сцена/логіка для Android WebView. `android/app/src/main/java/ua/mavka/caravan/MainActivity.java` — оболонка, локальний URL для asset bundle, ввімкнений DOM storage, повноекранний режим, обробка Back і onPause.
- **Наявна особливість:** `.github/workflows/build-caravan-automatic.yml` пакує `web/` і PNG локацій `painterly_v021`, **не** `game/v012_migration/` і **не** новий каталог зі 100 вирізками. Висновок: ці функції не можна вважати включеними до поточного APK.
- **Блокер міграції:** `game/v012_migration/index.html` звертається до `style.css` та `assets/wagons/...`, але повний пов'язаний пакет файлів відсутній у перевіреній гілці. Логіку v0.12 не можна просто оголосити робочим Android-клієнтом.
- **CI:** перевірка існування всіх asset paths, перевірка SHA-256, JS syntax/smoke, збірка debug APK, ZIP/signature validation, тест запуску Android, ручний графічний QA. Зберігати релізні артефакти й короткий протокол.
- **Сумісність оновлень:** для встановлюваного Android-продукту потрібні постійні application ID / signing key та міграція локального збереження. У поточній збірці debug ключ може змінюватися, а package ID тестовий.
- **Продуктивність:** для цільових бюджетних Android-пристроїв — стабільна взаємодія, обмеження завантажуваних текстур, відсутність мерехтіння й блокувань; вимірювані FPS, пам'ять і час старту фіксувати під час тестування, не вигадувати результати заздалегідь.

## 11. Регламент статусів та приймання

| Статус | Коли застосовувати |
|---|---|
| BACKLOG | Є вимога, реалізацію не почато. |
| IN_PROGRESS | Є неповна реалізація; зазначений шлях і власне наступне завдання. |
| CODE_READY | Код/графіка є, але немає повного тесту в основній APK. |
| TESTING | Робоча APK з функцією існує, збираються результати тестування. |
| DONE | Функція доступна в поточній APK, пройшла критерії та Android-регресію. |
| BLOCKED | Названо точну відсутню залежність або проблему. |

У `docs/CARAVAN_TASK_STATUS.json` кожна робота має ID, етап, статус, залежності, доказ і критерій прийняття. При наступних релізах змінювати цей файл разом із кодом. **Розроблена картинка, напис у README або успішний компілятор самі по собі не переводять функцію в DONE.**

## 12. Невизначені рішення — не видавати за погоджені

1. Детальна економіка п'яти валют і можливі способи їх отримання/витрат: художні назви є, правил немає. Для MVP достатньо основних ресурсів і однієї базової валюти за узгодженим балансом.
2. Бойова система, фракції, сюжет і рівні складності: у двох наданих документах **не специфіковано**; потрібно окреме геймдизайнерське доповнення.
3. Постійна зміна погоди/денний цикл, кількість вагонів понад три, процес прийому пасажирів і взаємодія станцій мають бути збалансовані після завершення основної технічної вертикалі.
4. Вирізані графічні картки з власним фоном і ізольовані прозорі спрайти — різні типи ресурсу; не підміняти один іншим.
